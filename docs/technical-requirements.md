# Technical Requirements Document

## 1. Reference architecture

```text
React/Vite web ── HTTPS/JSON ── FastAPI ── SQLAlchemy ── PostgreSQL/Supabase
       │                              │
       └── shared contracts            └── session cookie + OAuth provider

Future ESP32 ── MQTT/HTTP contract ── ingestion boundary ── FastAPI
Future Flutter ── HTTPS/JSON ────────────────┘
```

The browser and mobile clients use Supabase Auth and protected PostgREST/RPCs,
plus the FastAPI HTTP API where implemented. They do not open raw PostgreSQL,
MQTT, or hardware connections. Time-sensitive automation remains local to the
device. See SETUP.md at the repository root for the current configuration.

## 2. Required technology

- Frontend: React 19, TypeScript, Vite, Tailwind CSS, semantic HTML, inline
  SVG icons, and Recharts when charts are implemented.
- Backend: Python 3.12+, FastAPI, Pydantic, SQLAlchemy 2, Alembic, psycopg,
  and pytest/Ruff.
- Data: PostgreSQL as the supported relational database; Supabase is an
  optional hosted PostgreSQL provider.
- Delivery: Docker Compose for local API/database/MQTT services and GitHub
  Actions for repeatable validation.
- Mobile: Flutter/Dart consumes the same versioned HTTP contracts.

## 3. API rules

- All application routes use `/api/v1`.
- JSON errors use a stable `detail` message and appropriate HTTP status.
- Resources use immutable integer or UUID identifiers and ISO-8601 UTC times.
- List routes define pagination, stable ordering, and filter behavior.
- Request payloads are validated at the API boundary.
- Authorization is checked against the authenticated user and resource owner.
- OpenAPI generated by FastAPI is the source of truth for implemented routes.
- Mutating routes must be idempotent where retries are expected.

## 4. Data and security

- Store password-free provider identity fields; Supabase manages authentication.
- Verify Supabase bearer tokens and enforce role/ownership checks on the API and RLS boundaries.
- Never log OAuth codes, session tokens, credentials, or personal secrets.
- Use foreign keys, check constraints, indexes, and migration review for
  operational data.
- Keep source occurrence time separate from server receipt time for telemetry.
- Use audit records for privileged changes and operational state transitions.

## 5. Reliability and observability

The API shall expose liveness and readiness separately when infrastructure is
introduced. Logs must be structured enough to correlate a request, user, batch,
and device event without exposing secrets. Health checks, backup/restore,
migration rollback, alerting, and a deployment runbook are release gates.

## 6. Current implementation slice

The first implementation slice adds a batch resource and migration, protected
list/create/update/archive routes, and a grower dashboard that consumes the
resource. Telemetry, watering automation, and device commands remain explicit
unavailable states until their contracts and safety evidence are complete.
